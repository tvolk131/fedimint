# First Simplicity resource baseline — 2026-10-02

The measurements support doing more than adjusting the static-cost fee
coefficient. Decoding and transaction context are material costs, and the current
per-input limits permit a transaction taking about **0.81 seconds of module
validation** on this machine. This pass changes no fees, limits or production
Rust. These are measured examples, not proven worst cases or production sizing.

## Method and reproducibility

Production code: `d748fb05f031f13f299e77299bad849d7c786222`, with the benchmark
harness added by this commit. Apple M4 Pro, 14 cores, 48 GiB RAM, macOS 26.6.2;
Rust 1.98.1, native ARM64, default optimized bench profile with thin LTO. Divan
0.1.21, System allocator, 100 samples of one iteration per operation. Two timing
runs and a separate allocation-profiler build. No concurrent builds; no CPU
pinning, thermal controls or load isolation. Timing precision was 41 ns.

The following are first-input measurements. Fee is the current experimental
input fee, including encoded bytes; no economic conclusion is drawn from its
absolute value. Runtime includes decode and VM; the cached-VM measurement excludes

For the market issuance path, decoding takes roughly 1.1 ms, versus about 0.05 ms
for the cached VM. A 4 KiB constant takes about 4.2 ms to decode despite a low
static execution cost. Byte pricing therefore matters independently of the
execution-cost coefficient; profiling the decoder is justified before tuning it.

The unit-combinator and signature workloads both sit near the static cost cap,
but the signature workload takes over 50 times as long. Static cost is a bound,
not an exact runtime prediction; this variation does not by itself show the bound
is unsound. Calibration must cover the expensive jet mix as well as cheap
combinators, and include the decoder and Fedimint adapter overhead.

## Context and rejected work

Going from 8 to 32 trivial inputs costs about 8 times as much validation in these
fixtures. Adding 32 outputs raises it further, and filling those outputs with
recovery bytes or assets raises it again. The implementation recomputes the same
version-specific intent hash and clones the resolved context for each input.
In run 2, one intent hash takes about 76 microseconds for `recovery_32` and
87 microseconds for `assets_32`; one environment clone takes only about 3
microseconds in each. These isolated measurements and the code identify repeated
hashing as a candidate to profile/cache within validation. They are not a direct
measurement of total context-construction time or proof of an exact asymptotic
bound.

The invalid oracle path costs about as much as valid resolution. A wrong
signature in the last of 32 owner inputs costs about 6.7–7.1 ms before rejection.
A conservation failure in the large asset context rejects earlier (about
0.14 ms). Rejected transactions do not pay the accepted transaction fee, so fee
calibration alone cannot control invalid-submission resource use.

Truncated huge words and impossible node counts show no allocations. The
exponential-type rejection takes about 10 microseconds with 24.94 KB peak
additional heap. Oversized byte-vector rejections are near/below timer precision;
the printed zero-nanosecond medians do not mean zero work. Existing allocation
regression tests, rather than timing thresholds, check these early guards.

Across this matrix, peak additional Rust heap is modest relative to CPU cost.
Market validation peaks at about 315 KB; the largest intermediate-value VM at
about 132 KB. Sequential validation of 32 programs does not require 32 simultaneous
VM allocations. This does not bound a guardian's process memory under concurrent
admission, larger databases, other modules or malicious inputs outside this matrix.

## Implications for the next pass

1. Discuss a transaction-wide work budget before choosing production limits.
   Input count times per-program cost currently allows roughly 319 million
   milliweight in a very small transaction. Include aggregate decoding/context
   work and multiple module instances in that discussion.
2. Profile and consider reusing version-specific intent hashes and immutable
   resolved context within one validation call. Consider the duplicate decode
   across core verification and module execution separately, preserving consensus
   checks and avoiding an unbounded global cache. Re-measure after any change.
3. Keep fee components for encoded data and VM work distinct. Do not fit one
   coefficient to the market example or claim a universally accurate time-to-cost
   conversion from these samples.
4. Measure the full admission/consensus path on intended guardian hardware,
   including RocksDB, repeated invalid submissions and concurrency. Admission
   resource controls must address rejected work independently of paid fees.

Before production calibration, extend the matrix to creation signatures, all
market branches, combined decoder/type/frame limits and adversarial canonical
encodings. Repeat on Linux guardian-class hardware. Recovery-history storage and
scan costs are a separate measurement problem. This single-Mac baseline does not
close the broader security/determinism hardening item.
