# Federated BOLT12 offline receives

Status: experimental design for the `federated-bolt12` branch. Not reviewed by a
cryptographer. Not for real funds.

A wallet registers a reusable BOLT12 offer with the federation and goes offline.
Payers request invoices over onion messages; a gateway relays the request, the
guardians threshold-sign an invoice under a federation key, and the gateway
funds a claim for the recipient once it holds the Lightning payment. The
recipient claims later with its mnemonic-derived key. A gateway is trusted for
availability only.

This document specifies recipient-supplied stock and the pool of preimages the
guardians generate by MPC.

## Trust and parameters

- `n` guardians, `f = (n - 1) / 3`, quorum `q = n - f`. Requires `n >= 4`.
- Invoice signing uses a dedicated FROST (BIP340) key with threshold `q`,
  generated by DKG at federation setup. Preimage release uses LNv2's existing
  threshold encryption key (`tpe`).
- Enabled only when configuration is generated with
  `FM_ENABLE_FEDERATED_BOLT12=1`. Existing federations cannot enable it.
- Only gateways approved by a guardian quorum may reserve invoices.

## Preimage sources

Every invoice consumes one single-use (payment hash, encrypted preimage) pair.
A payment hash that has appeared in a reservation is never issued again: the
holder of the first invoice would gain a forged proof of payment, and a late
payment could expose the preimage of a live invoice.

1. **Stock** (this milestone). The recipient uploads pairs it generated itself:
   `ciphertext = tpe::encrypt(agg_pk, seed, preimage, binding)` with
   `binding = H("fedimint/bolt12/stock/v1", registration, index, payment_hash)`.
   Guardians cannot check that the ciphertext holds the right preimage, so a
   funded receive keeps LNv2's refund path: if the decrypted value does not hash
   to the payment hash, the gateway reclaims its funding.
2. **Pool**. Committees of guardians jointly generate payment hashes whose
   preimage nobody knows; see Generation. A registration opts in with
   `allow_pool`, and a reservation may use the pool only once the
   registration's stock is exhausted. The recipient pays `pool_fee` on top of
   the ordinary fee when it claims such a receive.

## Consensus state

All state is in indexed tables; nothing is stored as one aggregate value.

| Table | Key | Value |
|---|---|---|
| Registration | `RegistrationId` | `Registration` |
| Handle index | `handle: [u8; 32]` | `RegistrationId` |
| Recipient index | `claim_pk` | `RegistrationId` |
| Expiry index | `(expires_at, RegistrationId)` | `()` |
| Stock | `(RegistrationId, index: u64)` | `StockItem` |
| Payment hash index | `payment_hash` | `()` |
| Reservation | `ReservationId` | `Reservation` |
| Offer pending list | `RegistrationId` | `Vec<Pending>` (bounded) |
| Gateway pending list | gateway key | `Vec<Pending>` (bounded) |
| Gateway vote | `(gateway key, PeerId)` | `bool` |
| Receive contract | `OutPoint` | `ReceiveContract` |
| Receive stream | `u64` | `OutPoint` |
| Decryption shares | `OutPoint` | `Vec<DecryptionKeyShare>`, one per ciphertext |
| Pool item | `index: u64` | `PoolItem` |
| Pool next index | singleton | `u64` |
| Pool pending list | singleton | `Vec<Pending>` (bounded) |
| Generation run | singleton | `PoolRun` |
| Run counter | singleton | `u64` |
| Run submission | `(run, PeerId)` | `Vec<PoolShare>` |
| Abandoned run | `run` | `AbandonedRun` (committee, submitters, evidence commitments) |
| Verdict | `(run, PeerId)` | `PoolVerdict` |
| Guardian blame | `PeerId` | `Blame { offences, until_run }` |
| Pair dispute | `(PeerId, PeerId)` | `Blame { offences, until_run }` |

```text
Registration {
    policy: ReceivePolicy,
    stock_len: u64,        // number of stock items ever uploaded
    stock_next: u64,       // all indices below this are used
    voided: bool,          // set when a stock item decrypted to a wrong preimage
}
ReceivePolicy {
    handle: [u8; 32],      // random; embedded in the offer metadata
    claim_pk: PublicKey,   // per-offer key derived from the wallet secret
    offer_hash: sha256,    // hash of the exact offer TLV bytes
    max_gateway_fee: PaymentFee,
    expires_at: u64,
    allow_pool: bool,
}
StockItem { payment_hash: [u8; 32], ciphertext: CipherText }
Source = Stock { index } | Pool { index }
Sealed =
    Preimage(CipherText)   // stock: the recipient's preimage
  | Shares { run, threshold, shares: Vec<{ position, ciphertext }> }
PoolItem { payment_hash, sealed: Sealed::Shares }
PoolRun { run, committee: Vec<PeerId>, batch, started_at }
Reservation {
    registration: RegistrationId,
    source: Source,
    payment_hash: [u8; 32],
    sealed: Sealed,
    claim_pk: PublicKey,
    gateway: PublicKey,
    amount: Amount,        // invoice amount
    gateway_fee: Amount,
    terms: sha256,         // H(invoice request bytes, payment path bytes)
    created_at: u64,
    funded: Option<OutPoint>,
}
ReceiveContract {
    reservation: ReservationId,
    registration: RegistrationId,
    source: Source,
    payment_hash: [u8; 32],
    sealed: Sealed,
    amount: Amount,        // invoice amount minus gateway fee
    gateway_fee: Amount,
    claim_pk: PublicKey,
    refund_pk: PublicKey,  // the gateway
}
```

Consensus never parses a BOLT12 offer, invoice request or payment path. Those
are opaque bytes pinned by hash and validated by guardians when they sign.

## Transactions

Outputs (`LightningOutputV0`):

- `Bolt12Register { policy, signature }`. Signed by `claim_pk`. Requires an
  unexpired policy with `expires_at` at most one year ahead, an unused handle and
  claim key, and fewer than `MAX_REGISTRATIONS` live registrations. Costs
  `registration_fee`. Processing first deletes up to a fixed number of expired
  registrations (and their unused stock) found through the expiry index.
- `Bolt12AddStock { registration, start, items, signature }`. Signed by
  `claim_pk`. `start` must equal `stock_len`, `items` holds 1 to 64 entries, each
  ciphertext must verify against its binding, each payment hash must be new
  federation-wide, and `stock_len` may not exceed `MAX_STOCK`. Costs
  `stock_item_fee` per item.
- `Bolt12Reserve { registration, source, gateway, amount, gateway_fee, terms,
  signature }`. Signed by `gateway`, which must be approved. Zero amount and
  zero fee. Requires a live, non-voided registration, an unused stock item at
  `source`, `gateway_fee <= max_gateway_fee.fee(amount)`, and
  `amount > gateway_fee + funding fees` (the recipient nets more than zero).
  Enforces the pending limits below. A duplicate reservation is an error, not a
  silent success. The stock item is deleted. A `Pool { index }` source also
  requires `allow_pool`, no unused stock, and a pool item at `index`, which is
  deleted; the economical check then includes `pool_fee`.
- `Bolt12Receive { reservation }`. Value `amount - gateway_fee`. Requires an
  unfunded reservation whose invoice has not expired. Creates the receive
  contract, appends it to the receive stream, stores this guardian's decryption
  share for every ciphertext, and removes the reservation from the pending
  lists. Costs the normal LNv2 fee plus `receive_fee`.

Input (`LightningInputV0`):

- `Bolt12Receive(outpoint, Bolt12Unlock)`. `Bolt12Unlock` is `Stock(key)` or
  `Pool(keys)`, matching the contract's source, with one aggregate decryption
  key per ciphertext; each must verify against its ciphertext and binding. If
  the decrypted stock value, or the preimage reconstructed from the decrypted
  shares, hashes to the payment hash, the input is spendable by `claim_pk`;
  otherwise by `refund_pk`, and a stock registration is voided. A `Pool` input
  costs `pool_fee` on top of the ordinary fee, on the claim and on the refund
  alike, so a client can price it without reading the contract.

Consensus items:

- `Bolt12GatewayVote { gateway, approve }`. Each guardian's latest vote is
  stored; a gateway is approved while at least `q` guardians vote to approve.
  Guardians set their vote through an authenticated admin endpoint.
- `Bolt12PoolStart { run }`, `Bolt12PoolShares { run, shares }`,
  `Bolt12PoolAbandon { run }`, `Bolt12PoolEvidence { run, digest }` and
  `Bolt12PoolVerdict { run, verdict }`; see Generation and Blame.

## Limits

Unpaid invoice requests cost the federation work and cost the recipient stock,
and nobody can be charged for them: the payer is anonymous and the gateway is
never asked to pay before it holds the Lightning payment. They are bounded
instead.

- A reservation is *pending* from creation until it is funded or its invoice
  expires (`INVOICE_LIFETIME`, 600 seconds of consensus time).
- At most `MAX_PENDING_PER_OFFER` (8) pending reservations per registration and
  `MAX_PENDING_PER_GATEWAY` (64) per gateway. Each list is a bounded vector of
  `(expires_at, ReservationId)`; expired entries are dropped, and their
  reservations deleted, whenever the list is next touched.
- At most `MAX_PENDING_POOL` (32) pending reservations use the pool at once,
  across all offers, so unpaid requests cannot drain it faster than runs
  refill it.
- Paid receives leave the lists immediately, so only unpaid requests consume
  allowance.
- Guardians can withdraw their vote for a gateway that abuses its allowance.

## Invoice signing

Signing is outside consensus and needs only a quorum.

1. The gateway sends each guardian `(reservation, attempt, invoice request
   bytes, payment path bytes)` signed with its gateway key.
2. A guardian checks that the bytes hash to the reservation's `terms`, parses
   them, and requires: the request's offer TLVs hash to `offer_hash`; the chain
   matches; quantity is absent or one; the request amount equals `amount`. It
   then builds the canonical unsigned invoice from the request, the single
   payment path, the reservation's payment hash, `created_at` and
   `INVOICE_LIFETIME`.
3. FROST round one returns a nonce commitment; round two signs only the digest
   of that canonical invoice. Nonces live in memory, each is used once, and a
   durable marker is written before a commitment or share is returned. A
   restarted guardian cannot resume old attempts. Attempts per reservation are
   capped.

If a gateway pins terms that guardians reject, no invoice exists and the stock
item is burned against that gateway's allowance.

## Receive flow

1. Wallet: derive a per-offer key, collect onion-message ingress paths from one
   or more gateways, build the offer under the federation's FROST key with
   metadata `prefix || federation id || handle`, register it,
   and upload stock. Preimages and encryption seeds are derived from the offer
   secret and the stock index, so a restored wallet can top up.
2. Gateway, on an invoice request: resolve the handle, pick the lowest unused
   stock item, register its payment hash with its Lightning node to obtain a
   blinded payment path, submit `Bolt12Reserve`, coordinate signing, cache the
   invoice and reply.
3. Gateway, on the held payment: check hash, amount and claim deadline, then
   submit `Bolt12Receive`. After acceptance it collects decryption shares,
   decrypts the preimage and settles the payment. If the preimage is wrong it
   fails the payment and reclaims the contract.
4. Wallet, when next online: scan the receive stream for its claim keys,
   collect decryption shares and claim.

## Generation

The pool is enabled when `pool_target > 0`. Each guardian proposes
`Bolt12PoolStart { run }` while no run is in progress and fewer than
`pool_target` items are ready; the first one ordered starts run `run` (the run
counter's value), recording its committee, `pool_batch` and the consensus
time.

- **Committee.** `2f + 1` guardians taken in `PeerId` order starting at
  offset `run mod n` and wrapping, skipping blamed guardians and never seating
  both guardians of a disputed pair (see Blame). A member's position in the
  committee is its party index in the MPC.
- **MPC** (`fedimint-mpc`). Degree-`f` Shamir sharing over GF(2^64) among the
  committee, which is honest-majority with abort because at most `f` members
  are malicious. Each member's contributions are XORed into `r`; the circuit
  publishes `SHA256(r)` and gives each member its share of `r` (threshold
  `f + 1`) masked under a key only that member supplied. Malicious members can
  make a run abort but not change its output or learn `r`.
- **Transport.** Members exchange messages through the module API endpoint
  `bolt12_mpc`. Each message is Schnorr-signed by its sender under its
  transport key, bound to run, sender, recipient and round, then chunked and
  encrypted with ChaCha20-Poly1305 under a key from the two guardians'
  transport keys, bound to run, direction, round and chunk. Senders retry
  until the recipient reaches the round. Recipients keep every message with
  its signature.
- **Durability.** Before sending anything, a member records the run and the
  seed all its randomness comes from. A restarted member does not rejoin; the
  run times out instead.
- **Submission.** A member that finishes encrypts each share to the
  federation's TPE key, bound to `(run, position, payment_hash)`, stores the
  result and proposes `Bolt12PoolShares`. Consensus checks the sender is a
  member, the count matches the batch and every ciphertext verifies.
- **Completion.** When every member has submitted, the hash list submitted by
  at least `f + 1` members (the honest ones always agree, and are a majority)
  becomes pool items, sealed with the shares of the members who submitted it.
  Hashes already seen are skipped. The run and its submissions are deleted.
- **Timeout.** Once the consensus time passes `started_at +
  POOL_RUN_TIMEOUT` (900 s), guardians propose `Bolt12PoolAbandon { run }`,
  which deletes the run and its submissions and records it for judging.
  Results of an abandoned run are never used, so no share of a
  later-published preimage ever leaves a member.
- **Release.** Funding a pool receive stores each guardian's decryption share
  for every member's ciphertext. The gateway and the recipient aggregate a
  threshold of these per ciphertext, decrypt the `2f + 1` shares and
  reconstruct `r` by trying subsets of `f + 1` until one hashes to the payment
  hash. At least `f + 1` shares come from honest members, so this succeeds
  whatever the others sealed.

### Blame

A run fails when a member deviates, stays silent, or finishes without
submitting. Every message a member sends is a deterministic function of its
seed and the messages it received, so once a run is abandoned and its
results can never be used, the run can be replayed.

1. **Evidence.** When its part in a run ends, a member stores the signed
   messages it received. If consensus abandons the run, the member proposes
   `Bolt12PoolEvidence { run, digest }`, committing to its seed and those
   messages, within `EVIDENCE_WINDOW` (300 s), and serves them through the
   `bolt12_mpc_evidence` endpoint, which refuses to reveal anything about a
   run that has not been abandoned.
2. **Judging.** After the window, every guardian fetches the committed
   evidence, discards messages whose sender's signature does not verify,
   replays each member, and compares what each member should have sent with
   what the others hold under its signature. In this order it finds:
   members that committed no evidence or whose evidence cannot be fetched or
   does not match; members whose signed messages differ from their replay,
   or who hold back received messages that their later signed messages prove
   they had; members whose replay completes but who did not submit. Only if
   nobody is at fault does it report disputes: for the earliest round in
   which a member lacks a message, the pair of that member and the missing
   sender. One of them is at fault, but not provably which.
3. **Verdicts.** Each guardian proposes `Bolt12PoolVerdict { run, verdict }`.
   Once a quorum has voted, every culprit and every pair named by at least
   `f + 1` verdicts is blamed: honest guardians replay the same evidence to
   the same verdict, and `f` malicious guardians cannot reach `f + 1`
   alone. No new run starts while a run is being judged, up to
   `JUDGE_TIMEOUT` (1800 s), after which it is dropped unjudged.
4. **Exclusion.** A blamed guardian sits out the next 8 runs, a disputed pair
   never shares a committee for 8 runs, and each repeat doubles that, up to
   64. Completing a run clears its members' blame and their mutual disputes.
   Honest guardians are never blamed and never dispute each other, and there
   are at least `2f + 1` of them, so a committee without blamed guardians or
   disputed pairs exists unless honest guardians failed. If it does not, the
   committee ignores disputes, and if it must, seats the blamed guardians
   released soonest: a committee never has fewer than `2f + 1` members.

Reasoning recorded for review: openings check that all `2f + 1` shares lie on
one degree-`f` polynomial, which the `f + 1` honest shares fix, so no digest
echo per opening is needed; the challenge for the triple check is drawn by
commit and reveal with an echoed commitment. Before a share leaves the MPC it
is known only to its member; after sealing, decrypting it needs a quorum, and
consensus only releases decryption shares once a receive is funded.

## Gateway

- `POST /bolt12_ingress` with a federation id returns the gateway's blinded
  onion-message path, its reservation key and its receive fee, or `null` when
  it does not serve federated BOLT12 offers for that federation. Wallets use
  `LightningClientModule::bolt12_gateways` to collect these from several
  gateways and drop the ones the federation has not approved.
- The Lightning node hands invoice requests whose offer metadata carries the
  routing prefix to the gateway instead of answering them itself. The gateway
  answers up to 16 at once, each within 60 seconds, and drops the rest; payers
  retry. Requests share the gateway's invoice rate limit.
- A held payment is matched against every connected federation's issued
  BOLT12 invoices by payment hash, after LNv2 and before LNv1. A payment whose
  amount differs from the invoice is failed back unfunded.
- Payment paths ask payers for a 144-block final CLTV delta. A blinded path's
  delta lives in its payinfo and cannot be enforced by the receiving node, so
  the gateway funds a claim only if the held HTLC leaves at least 36 blocks
  before its claim deadline; otherwise it fails the payment back unfunded.
- Only the LDK backend serves these offers. It needs the `fedimint-ldk-node`
  patch on branch `fedimint-federated-bolt12` of `tvolk131/ldk-node`, which
  routes externally issued invoice requests to the gateway and registers
  payment hashes whose preimage the node does not know. Other backends report
  the feature as unsupported.
- Payment paths are one hop, introduced by the gateway's node. Payers running
  `lightning` 0.2.7 or older ignore a one-hop path's CLTV delta and their HTLCs
  fall short of the margin; 0.2.8 fixed this.

## Fees and minimum amounts

`Bolt12Config` carries `registration_fee`, `stock_item_fee`, `receive_fee`,
`pool_fee`, `pool_target` and `pool_batch`.
There is no separate minimum-amount setting. The single rule is that a
reservation's amount must exceed every fee taken for the source it uses, so the
recipient always nets more than zero. Pool-backed receives will add a premium to
that sum, which raises their effective minimum without affecting stock-backed
ones. Wallets should warn when fees are a large share of the amount.

The gateway pays `receive_fee` when it funds a receive and passes it on in
its own fee. The recipient pays `pool_fee` when it claims a pool receive,
because it chose the pool.

## Privacy

Each offer has its own claim key, so a wallet's offers are not linked to each
other or to its LNURL key through federation state. Receives for one offer are
publicly linkable to that offer, including their amounts. Hiding that conflicts
with guardians verifying that funds go to the registered recipient and is out of
scope.

## Deferred

- An end-to-end test of blame against a misbehaving guardian; blame is
  covered by unit tests of the judge and of the consensus rules.
- Taking share coefficients and masks from the MPC's own shared randomness
  instead of bit-checked inputs, which would make runs cheaper.
- Payment paths through the gateway's channel peers, which older payers
  handle correctly and which hide the gateway node behind its peers.
- Open (non-approved) gateways backed by a recipient deposit.
- Enabling the feature on an existing federation.
