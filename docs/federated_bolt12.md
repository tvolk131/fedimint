# Federated BOLT12 offline receives

Status: experimental proof-of-concept standalone Fedimint module (`ModuleKind("bolt12")`)
on the `federated-bolt12-module` branch. Not reviewed by a cryptographer. Not for real funds.

A wallet registers a reusable BOLT12 offer with the federation and goes offline.
Payers request invoices over onion messages; a gateway relays the request, the
guardians threshold-sign an invoice under a federation key, and the gateway
funds a claim for the recipient once it holds the Lightning payment. The
recipient claims later with its mnemonic-derived key. A gateway is trusted for
availability only.

This document specifies recipient-supplied stock, the MPC-generated preimage
pool, operator CLI commands, Prometheus metrics, and a local Mutinynet PoC
runbook.

## Trust and parameters

- `n` guardians, `f = (n - 1) / 3`, quorum `q = n - f`. Requires `n >= 4`.
- Invoice signing uses a dedicated FROST (BIP340) key with threshold `q`,
  generated by DKG at federation setup. Preimage release uses the module's own
  threshold encryption key (`tpe`), also generated by DKG at setup.
- Implemented as a standalone module (`fedimint-bolt12-{common,server,client}` +
  `fedimint-gw-bolt12-client`) with no dependency on `fedimint-lnv2-*`.
- Attached to `fedimintd` only when `FM_ENABLE_FEDERATED_BOLT12=1` is set during
  setup/startup. Existing federations cannot enable it.
- Pool parameters default to `DEFAULT_POOL_TARGET = 32` and
  `DEFAULT_POOL_BATCH = 8`, and may be overridden at DKG time via
  `FM_BOLT12_POOL_TARGET` (in `0..=256`) and `FM_BOLT12_POOL_BATCH` (in
  `1..=32`). Guardians explicitly agree on `(public_package, pool_target,
  pool_batch)` during DKG.
- Only gateways approved by a guardian quorum may reserve invoices.

## Preimage sources

Every invoice consumes one single-use (payment hash, encrypted preimage) pair.
A payment hash that has appeared in a reservation is never issued again: the
holder of the first invoice would gain a forged proof of payment, and a late
payment could expose the preimage of a live invoice.

1. **Stock.** The recipient uploads pairs it generated itself:
   `ciphertext = tpe::encrypt(agg_pk, seed, preimage, binding)` with
   `binding = H("fedimint/bolt12/stock/v1", registration, index, payment_hash)`.
   Guardians cannot check that the ciphertext holds the right preimage, so a
   funded receive keeps LNv2's refund path: if the decrypted value does not hash
   to the payment hash, the gateway reclaims its funding.
2. **Pool.** Committees of guardians jointly generate payment hashes whose
   preimage nobody knows; see Generation. A registration opts in with
   `allow_pool`, and a reservation may use the pool only once the
   registration's stock is exhausted. The recipient pays `pool_fee` on top of
   the ordinary fee when it claims such a receive.

## Consensus state

All state is in indexed tables; nothing is stored as one aggregate value.

| Table | Key | Value |
|---|---|---|
| Registration | `RegistrationId` | `Registration` |
| Handle index | `handle: [u8; 32]` | `RegistrationId` |
| Recipient index | `claim_pk` | `RegistrationId`; kept after pruning |
| Expiry index | `(expires_at, RegistrationId)` | `()` |
| Stock | `(RegistrationId, index: u64)` | `StockItem` |
| Payment hash index | `payment_hash` | `()` |
| Reservation | `ReservationId` | `Reservation` |
| Offer pending list | `RegistrationId` | `Vec<Pending>` (bounded) |
| Gateway pending list | gateway key | `Vec<Pending>` (bounded) |
| Gateway approval | `(gateway key, PeerId)` | `true`; only approvals are stored |
| Approval count | `PeerId` | `u64` |
| Receive contract | `OutPoint` | `ReceiveContract` |
| Receive stream | `u64` | `OutPoint` |
| Decryption shares | `OutPoint` | `Vec<DecryptionKeyShare>`, one per ciphertext |
| Pool item | `index: u64` | `PoolItem` |
| Pool next index | singleton | `u64` |
| Pool pending list | singleton | `Vec<Pending>` (bounded) |
| Generation run | singleton | `PoolRun` |
| Run counter | singleton | `u64` |
| Run submission | `(run, PeerId)` | `Vec<PoolShare>` |
| Abandoned run | `run` | `AbandonedRun` (committee, submitters, evidence commitments) |
| Verdict | `(run, PeerId)` | `PoolVerdict` |
| Guardian blame | `PeerId` | `Blame { offences, until_run }` |
| Pair dispute | `(PeerId, PeerId)` | `Blame { offences, until_run }` |

```text
Registration {
    policy: ReceivePolicy,
    stock_len: u64,        // number of stock items ever uploaded
    stock_unused: u64,     // stock items not yet consumed by a reservation
    voided: bool,          // set when a stock item decrypted to a wrong preimage
}
ReceivePolicy {
    handle: [u8; 32],      // random; embedded in the offer metadata
    claim_pk: PublicKey,   // per-offer key derived from the wallet secret
    offer_hash: sha256,    // hash of the exact offer TLV bytes
    max_gateway_fee: PaymentFee,
    expires_at: u64,
    allow_pool: bool,
}
StockItem { payment_hash: [u8; 32], ciphertext: CipherText }
Source = Stock { index } | Pool { index }
Sealed =
    Preimage(CipherText)   // stock: the recipient's preimage
  | Shares { run, threshold, shares: Vec<{ position, peer, ciphertext }> }
PoolItem { payment_hash, sealed: Sealed::Shares }
PoolRun { run, committee: Vec<PeerId>, batch, started_at }
Reservation {
    registration: RegistrationId,
    source: Source,
    payment_hash: [u8; 32],
    sealed: Sealed,
    claim_pk: PublicKey,
    gateway: PublicKey,
    amount: Amount,        // invoice amount
    gateway_fee: Amount,
    terms: sha256,         // H(invoice request bytes, payment path bytes)
    created_at: u64,
}
ReceiveContract {
    reservation: ReservationId,
    registration: RegistrationId,
    source: Source,
    payment_hash: [u8; 32],
    sealed: Sealed,
    amount: Amount,        // invoice amount minus gateway fee
    gateway_fee: Amount,
    claim_pk: PublicKey,
    refund_pk: PublicKey,  // the gateway
}
```

Consensus never parses a BOLT12 offer, invoice request or payment path. Those
are opaque bytes pinned by hash and validated by guardians when they sign.

## Transactions

Outputs (`Bolt12Output::V0`):

- `Register { policy, signature }`. Signed by `claim_pk`. Requires an
  unexpired policy with `expires_at` at most one year ahead, an unused handle and
  claim key, and fewer than `MAX_REGISTRATIONS` live registrations. Costs
  `registration_fee`. Processing first deletes up to a fixed number of expired
  registrations (and their unused stock) found through the expiry index. A
  pruned registration's claim key stays in the recipient index: it can never
  be registered again, and a wallet restored from its seed uses it to tell
  which offer indices it has used.
- `AddStock { registration, start, items, signature }`. Signed by
  `claim_pk`. `start` must equal `stock_len`, `items` holds 1 to 64 entries, each
  ciphertext must verify against its binding, each payment hash must be new
  federation-wide, and `stock_len` may not exceed `MAX_STOCK`. Costs
  `stock_item_fee` per item.
- `Reserve { registration, source, gateway, amount, gateway_fee, terms,
  signature }`. Signed by `gateway`, which must be approved. Zero amount and
  zero fee. Requires a live, non-voided registration, an unused stock item at
  `source`, `gateway_fee <= max_gateway_fee.fee(amount)`, and
  `amount > gateway_fee + funding fees` (the recipient nets more than zero).
  Enforces the pending limits below. A duplicate reservation is an error, not a
  silent success. The stock item is deleted. A `Pool { index }` source also
  requires `allow_pool`, no unused stock, and a pool item at `index`, which is
  deleted; the economical check then includes `pool_fee`.
- `Receive { reservation }`. Value `amount - gateway_fee`. Requires an
  unfunded reservation whose invoice has not expired. Creates the receive
  contract, appends it to the receive stream, stores this guardian's decryption
  share for every ciphertext, and removes the reservation from the pending
  lists. Costs the module fee plus `receive_fee`.

Input (`Bolt12InputV0`):

- `Receive(outpoint, Bolt12Unlock)`. `Bolt12Unlock` is `Stock(key)` or
  `Pool { keys, subset }`, matching the contract's source, with one aggregate
  decryption key per ciphertext; each must verify against its ciphertext and
  binding. For `Pool`, an optional `threshold`-sized `subset` of committee
  positions lets consensus verify the preimage in `O(t^2)` without subset
  search. If the decrypted stock value, or the preimage reconstructed from the
  decrypted shares, hashes to the payment hash, the input is spendable by
  `claim_pk`; otherwise by `refund_pk`, and a stock registration is voided. If
  exactly one pool share disagrees with the reconstructed polynomial, that peer
  is blamed (unique disagreement is sound for any `f >= 1`). A `Pool` input
  costs `pool_fee` on top of the ordinary fee, on the claim and on the refund
  alike, so a client can price it without reading the contract.

Consensus items (`Bolt12ConsensusItem`):

- `UnixTimeVote(u64)`. Guardian consensus clock vote (unix timestamp in seconds).
- `GatewayVote { gateway, approve }`. Each guardian's latest vote is
  stored; a gateway is approved while at least `q` guardians vote to approve.
  Guardians set their vote through an authenticated admin endpoint.
- `PoolStart { run }`, `PoolShares { run, shares }`,
  `PoolAbandon { run }`, `PoolAbort { run }`, `PoolEvidence { run, digest }` and
  `PoolVerdict { run, verdict }`; see Generation and Blame.

## Limits

Unpaid invoice requests cost the federation work and cost the recipient stock,
and nobody can be charged for them: the payer is anonymous and the gateway is
never asked to pay before it holds the Lightning payment. They are bounded
instead.

- A reservation is *pending* from creation until it is funded or its invoice
  expires (`INVOICE_LIFETIME`, 600 seconds of consensus time).
- At most `MAX_PENDING_PER_OFFER` (8) pending reservations per registration and
  `MAX_PENDING_PER_GATEWAY` (64) per gateway. Each list is a bounded vector of
  `(expires_at, ReservationId)`; expired entries are dropped, and their
  reservations deleted, whenever the list is next touched.
- At most `MAX_PENDING_POOL` (32) pending reservations use the pool at once
  across all offers, and at most `MAX_PENDING_POOL_PER_OFFER` (4) per single
  offer, so unpaid requests cannot drain the pool faster than runs refill it.
- Paid receives leave the lists immediately, so only unpaid requests consume
  allowance.
- Guardians can withdraw their vote for a gateway that abuses its allowance.
  Each guardian approves at most `MAX_APPROVALS_PER_GUARDIAN` (256) gateways
  at once, and a withdrawn approval is deleted, so votes cannot grow state
  without bound.

## Invoice signing

Signing is outside consensus and needs only a quorum.

1. The gateway sends each guardian `(reservation, attempt, invoice request
   bytes, payment path bytes)` signed with its gateway key.
2. A guardian checks that the bytes hash to the reservation's `terms`, parses
   them, and requires: the request's offer TLVs hash to `offer_hash`; the chain
   matches; quantity is absent or one; the request amount equals `amount`. It
   then builds the canonical unsigned invoice from the request, the single
   payment path, the reservation's payment hash, `created_at` and
   `INVOICE_LIFETIME`.
3. FROST round one returns a nonce commitment; round two signs only the digest
   of that canonical invoice. Nonces live in memory, each is used once, and a
   durable marker is written before a commitment or share is returned. A
   restarted guardian cannot resume old attempts. Attempts per reservation are
   capped at 16 in total and 2 at a time. Each guardian holds at most 64
   nonces, at most 16 of them for one gateway, and reclaims those of
   reservations that were funded, so a gateway that never finishes signing
   cannot crowd out the others.

If a gateway pins terms that guardians reject, no invoice exists and the stock
item is burned against that gateway's allowance.

## Receive flow

1. Wallet: derive a per-offer key, collect onion-message ingress paths from one
   or more gateways, build the offer under the federation's FROST key with
   metadata `prefix || federation id || handle`, register it,
   and upload stock. Preimages and encryption seeds are derived from the offer
   secret and the stock index, so a restored wallet can top up.
2. Gateway, on an invoice request: resolve the handle, pick the lowest unused
   stock item, register its payment hash with its Lightning node to obtain a
   blinded payment path, submit `Bolt12Reserve`, coordinate signing, cache the
   invoice and reply.
3. Gateway, on the held payment: check hash, amount and claim deadline, then
   submit `Bolt12Receive`. After acceptance it collects decryption shares,
   decrypts the preimage and settles the payment. If the preimage is wrong it
   fails the payment and reclaims the contract.
4. Wallet, when next online: scan the receive stream for its claim keys,
   collect decryption shares and claim.

## Generation

The pool is enabled when `pool_target > 0`. Each guardian proposes
`Bolt12PoolStart { run }` while no run is in progress and fewer than
`pool_target` items are ready; the first one ordered starts run `run` (the run
counter's value), recording its committee, `pool_batch` and the consensus
time.

- **Committee.** `2f + 1` guardians. Once a committee completes a run with
  unanimous agreement it stays sticky for up to `STICKY_COMMITTEE_RUNS` (32)
  consecutive runs before rotating; on abandonment or expiry, selection picks
  an undisputed, unblamed committee using lowest-dispute-degree ordering with
  bounded backtracking so large federations (`N >= 25`) never stall consensus
  CPU. A member's position in the committee is its party index in the MPC.
- **MPC** ([`fedimint-mpc`](https://github.com/tvolk131/fedimint-mpc)). Degree-`f` Shamir sharing over `GF(2^8)` among the
  committee (pool generation capped at `MAX_POOL_DEGREE = 7`, `N <= 24`, so
  worst-case `2f + 1` refund subset search stays within `C(15, 8) = 6,435`
  trials), evaluating a pure-Rust low-depth SHA-256 circuit (CSA + Sklansky +
  carry-skip, depth 456) in SIMD lanes with live-wire slot recycling.
  Double-random sharings use seed-expanded Vandermonde extraction; online
  multiplications use load-balanced parallel-king DN07 (`O(1)` per-guardian
  egress and CPU per gate); all `M` multiplications and input bit-checks are
  verified together via a 4-way recursive BBCGI19 inner-product proof over
  `GF((2^8)^16)` with composed Schwartz–Zippel soundness error at most
  `(M + 10k + 2) / 2^128` (~110-bit at `batch = 4`, ~103-bit at
  `MAX_TRIPLES = 30_000_000`) before any public output or share is opened.
  Malicious members can make a run abort but cannot change its output or learn
  `r`.
- **Transport and relay fallback.** Members exchange messages through
  `bolt12_mpc`. Each message is Schnorr-signed by its sender, split into
  chunks, encrypted with ChaCha20-Poly1305 under an ephemeral ECDH key derived
  deterministically from the sender's run seed (providing forward secrecy while
  live and deterministic verification after abandonment), and outer-signed with
  an `envelope_sig`. If direct delivery stalls past `RELAY_TRIGGER` (10 s), the
  recipient sends a signed `RelayRequest` to other committee members
  (`bolt12_mpc_relay`), which pull the opaque encrypted chunks from the sender
  via a signed `FetchRequest` (`bolt12_mpc_fetch`), verify `envelope_sig`, and
  forward them—or record a relay witness if the sender refuses.
- **Durability.** Before sending anything, a member records the run and the
  seed all its randomness comes from. A restarted member does not rejoin; the
  run aborts or times out instead.
- **Submission.** A member that finishes encrypts each share to the
  federation's TPE key, bound to `(run, position, payment_hash)`, stores the
  result and proposes `Bolt12PoolShares`. Consensus checks the sender is a
  member, the count matches the batch and every ciphertext verifies.
- **Completion.** When every member has submitted, the hash list submitted by
  at least `f + 1` members (the honest ones always agree, and are a majority)
  becomes pool items, sealed with the shares of the members who submitted it.
  Members whose hash list disagrees with the majority are blamed. Hashes
  already seen are skipped. The run and its submissions are deleted.
- **Early abort and timeout.** A committee member whose local MPC run aborts
  proposes `Bolt12PoolAbort { run }`; once `f + 1` members report an abort,
  consensus immediately abandons the run without waiting for timeout.
  Otherwise, once consensus time passes `started_at + POOL_RUN_TIMEOUT`
  (300 s), guardians propose `Bolt12PoolAbandon { run }`. Results of an
  abandoned run are never used, so no share of a later-published preimage ever
  leaves a member.
- **Release.** Funding a pool receive stores each guardian's decryption share
  for every member's ciphertext. The gateway and the recipient aggregate a
  threshold of these per ciphertext, decrypt the shares and reconstruct `r`
  over `GF(2^8)` using polynomial-time Berlekamp–Welch Reed–Solomon decoding
  (with subset fallback if more than `(n - threshold) / 2` shares are
  corrupted). At least `f + 1` shares come from honest members, so this
  succeeds whatever the others sealed.

### Blame

A run fails when a member deviates, stays silent, or finishes without
submitting. Every message a member sends is a deterministic function of its
seed and the messages it received, so once a run is abandoned and its results
can never be used, the run can be replayed.

1. **Evidence.** When its part in a run ends, a member stores the signed
   messages it received together with its relay witnesses and any
   envelope-signed packets that failed AEAD decryption. If consensus abandons
   the run, the member proposes `Bolt12PoolEvidence { run, digest }` within
   `EVIDENCE_WINDOW` (90 s) and serves them through `bolt12_mpc_evidence`,
   which refuses to reveal anything about a run that has not been abandoned.
   Once every committee member has committed evidence, the window closes early.
2. **Judging.** Once the evidence window closes, every guardian fetches the
   committed evidence, verifies message signatures, checks any reported
   `BadPacket`s against the sender's seed-derived ephemeral key, replays each
   member, and compares what each member should have sent with what the others
   hold under its signature. In this order it finds:
   members that committed no evidence or whose evidence cannot be fetched or
   does not match; members whose signed messages differ from their replay, who
   signed an undecryptable packet, or who hold back received messages that
   their later signed messages prove they had; members whose replay completes
   but who did not submit; and silent senders at the earliest stall round
   witnessed missing by at least `f` third-party relays (an honest sender can
   face at most `f - 1` colluding relays if a malicious recipient fakes a
   stall). Only if nobody is provably at fault does it report pairwise
   disputes.
3. **Verdicts.** Each guardian proposes `Bolt12PoolVerdict { run, verdict }`.
   Once a quorum has voted, every culprit and every pair named by at least
   `f + 1` verdicts is blamed. No new run starts while a run is being judged,
   up to `JUDGE_TIMEOUT` (600 s), after which it is dropped unjudged.
4. **Exclusion and slow decay.** A blamed guardian sits out the next 8 runs, a
   disputed pair never shares a committee for 8 runs, and each repeat doubles
   that, up to 64. Completing a clean run does not wipe accumulated offences
   immediately; instead, each offence level decays only after
   `BLAME_DECAY_RUNS` (16) clean runs, preventing sleeper-reset attacks. Honest
   guardians are never blamed and never dispute each other, and there are at
   least `2f + 1` of them, so a committee without blamed guardians or disputed
   pairs exists unless honest guardians failed. If it does not, the committee
   ignores disputes, and if it must, seats the blamed guardians released
   soonest: a committee never has fewer than `2f + 1` members.

Reasoning recorded for review: openings check that all `2f + 1` shares lie on
one degree-`f` polynomial, which the `f + 1` honest shares fix, so no digest
echo per opening is needed; the challenge for the triple check is drawn by
commit and reveal with an echoed commitment. Before a share leaves the MPC it
is known only to its member; after sealing, decrypting it needs a quorum, and
consensus only releases decryption shares once a receive is funded.

## Gateway

- `POST /bolt12_ingress` with a federation id returns the gateway's blinded
  onion-message path, its reservation key and its receive fee, or `null` when
  it does not serve federated BOLT12 offers for that federation. Wallets use
  `LightningClientModule::bolt12_gateways` to collect these from several
  gateways and drop the ones the federation has not approved.
- The Lightning node hands invoice requests whose offer metadata carries the
  routing prefix to the gateway instead of answering them itself. The gateway
  answers up to 16 at once, each within 60 seconds, and drops the rest; payers
  retry. Requests share the gateway's invoice rate limit.
- A held payment is matched authoritatively via `PaymentHashOwner` in
  `gateway_db` (covering both BOLT11 and BOLT12 across all connected
  federations) before falling back to legacy reservations. A BOLT12 payment
  whose owning federation is temporarily unloaded is left held rather than
  cancelled (avoiding cancelling an already-funded receive), while an
  intercepted forward for an unloaded federation is cancelled. A payment whose
  amount differs from the invoice is failed back unfunded. The gateway never
  issues invoices with one payment hash for two federations or across BOLT11
  and BOLT12, so a federation cannot copy another's published hash to capture
  its payments.
- Identical invoice requests are issued one at a time; a repeat waits for the
  first and returns its invoice rather than reserving a second hash.
- Payment paths ask payers for a 144-block final CLTV delta. A blinded path's
  delta lives in its payinfo and cannot be enforced by the receiving node, so
  the gateway funds a claim only if the held HTLC leaves at least 36 blocks
  before its claim deadline; otherwise it fails the payment back unfunded.
- Only the LDK backend serves these offers. It needs the `fedimint-ldk-node`
  patch on branch `fedimint-federated-bolt12` of `tvolk131/ldk-node`, which
  routes externally issued invoice requests to the gateway and registers
  payment hashes whose preimage the node does not know. Other backends report
  the feature as unsupported.
- Payment paths are one hop, introduced by the gateway's node. Payers running
  `lightning` 0.2.7 or older ignore a one-hop path's CLTV delta and their HTLCs
  fall short of the margin; 0.2.8 fixed this.

## Fees and minimum amounts

`Bolt12Config` carries `registration_fee`, `stock_item_fee`, `receive_fee`,
`pool_fee`, `pool_target` and `pool_batch`.
There is no separate minimum-amount setting. The single rule is that a
reservation's amount must exceed every fee taken for the source it uses, so the
recipient always nets more than zero. Pool-backed receives will add a premium to
that sum, which raises their effective minimum without affecting stock-backed
ones. Wallets should warn when fees are a large share of the amount.

The gateway pays `receive_fee` when it funds a receive and passes it on in
its own fee. The recipient pays `pool_fee` when it claims a pool receive,
because it chose the pool.

## Privacy

Each offer has its own claim key, so a wallet's offers are not linked to each
other or to its LNURL key through federation state. Receives for one offer are
publicly linkable to that offer, including their amounts. Hiding that conflicts
with guardians verifying that funds go to the registered recipient and is out of
scope.

## CLI

All federated BOLT12 commands live under `fedimint-cli module bolt12`:

- `status` — show the FROST `signing_key`, fees, `pool_target`/`pool_batch`,
  and live `pool_available` count.
- `gateways [--gateway <url>]... [--include-unapproved]` — query gateways'
  `/bolt12_ingress` metadata, verify signatures, and display their reservation
  `gateway_key`, receive fee, and quorum approval status.
- `list-gateway-urls` — list gateway URLs vetted by guardians on the `bolt12`
  module.
- `add-gateway <url>` / `remove-gateway <url>` — guardian admin commands to add
  or remove a vetted gateway URL for BOLT12 ingress discovery.
- `create-offer [--description <text>] [--stock <n>] [--expiry-secs <n>] [--allow-pool] [--gateway <url>]... [--max-gateway-fee <base>,<ppm>]` —
  register a reusable BOLT12 offer and upload initial stock.
- `list-offers` — list this wallet's offers together with live federation stock
  counts (`stock_len`, `stock_unused`, `voided`, `expires_at`).
- `add-stock <offer-index> <count>` — top up single-use preimages for an offer.
- `rescan-offers [--max-index <n>]` — extended seed-recovery probe across offer
  indices `0..max_index` (rewinds the receive stream cursor on discovery).
- `approve-gateway <gateway-key> [--url <url>]` / `revoke-gateway <gateway-key>` — guardian
  admin commands (pass `--our-id <peer> --password <api-password>`) to cast or
  withdraw a `GatewayVote` (optionally also vetting the gateway URL).
- `gateway-approved <gateway-key>` — check whether a gateway key currently has
  quorum approval.

## Metrics

Guardian Prometheus metrics (`fedimintd --bind-metrics`, prefixed with `fm_`):

- `fm_bolt12_pool_items` (gauge) — ready MPC-generated preimages in pool.
- `fm_bolt12_pool_runs_total{outcome}` (counter) — completed,
  `abandoned_timeout`, `abandoned_abort`, and `no_majority` runs.
- `fm_bolt12_pool_run_duration_seconds{outcome}` (histogram) — local
  wall-clock MPC run duration (`completed`, `aborted`, `consensus_ended`).
- `fm_bolt12_pool_blame_total{kind}` (counter) — `culprit`, `dispute`,
  `disagreeing_submission`, and `poisoned_share` blame events.
- `fm_bolt12_receives_total{source,outcome}` (counter) — `stock`/`pool`
  receives across `reserved`, `funded`, `claimed`, and `refunded`.

Gateway Prometheus metrics (`gatewayd --metrics-listen`, prefixed with `fm_`):

- `fm_gateway_bolt12_invoice_requests_total{outcome}` (counter) — `issued`,
  `error`, `timeout`, `dropped_duplicate`, and `dropped_busy`.
- `fm_gateway_bolt12_htlc_handling_duration_seconds{outcome}` (histogram) —
  `funded`, `held`, `cancelled`, and `unmatched`.

## Local Mutinynet PoC runbook

`scripts/dev/mutinynet-bolt12.sh` boots a local 4-guardian federation and LDK
gateway against Mutinynet (`https://mutinynet.com/api`, no local `bitcoind`
required), completes DKG, connects and quorum-approves the gateway, joins a
local `fedimint-cli` user wallet, and verifies live MPC pool replenishment and
Prometheus metrics:

```bash
# Build required binaries (once)
cargo build --bin fedimintd --bin fedimint-cli --bin gatewayd --bin gateway-cli

# Start the 4-guardian Mutinynet federation + LDK gateway
./scripts/dev/mutinynet-bolt12.sh start

# Inspect live status, gateway balances, and BOLT12 Prometheus metrics
./scripts/dev/mutinynet-bolt12.sh status

# Stop processes (or `clean` to remove /tmp/fm-bolt12-mutinynet)
./scripts/dev/mutinynet-bolt12.sh stop
```

Once started, fund the gateway's LDK on-chain address from
`https://faucet.mutinynet.com`, open a channel with inbound liquidity on
Mutinynet, peg in a small amount of ecash to cover the 100-sat offer
registration + stock fees, create an offer with
`fedimint-cli module bolt12 create-offer --allow-pool`, and pay the

## Deferred

- An end-to-end test of blame against a misbehaving guardian; blame is
  covered by unit tests of the judge and of the consensus rules.
- A lower-depth SHA-256 circuit (carry-lookahead adders): over a real
  network a run's time is dominated by its ~1,600 rounds, not its gates.
- Payment paths through the gateway's channel peers, which older payers
  handle correctly and which hide the gateway node behind its peers.
- Open (non-approved) gateways backed by a recipient deposit.
- Enabling the feature on an existing federation.
